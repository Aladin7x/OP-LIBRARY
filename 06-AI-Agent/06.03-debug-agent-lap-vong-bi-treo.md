# Debug Agent bị lặp vòng hoặc bị treo

## Mục tiêu
Xác định chính xác nguyên nhân agent lặp vòng (gọi lại cùng 1 tool nhiều lần không tiến triển) hoặc bị treo (không dừng, không trả kết quả), và sửa được trong vòng 1 phiên debug — không phải đoán mò rồi viết lại toàn bộ prompt từ đầu.

## Khi nào dùng
- Agent gọi đi gọi lại cùng 1 tool với input gần giống nhau, không hội tụ về kết quả.
- Agent chạy quá lâu so với kỳ vọng (task đáng lẽ 3-4 bước nhưng chạy 20+ bước).
- Agent trả lời "đã xong" nhưng output rỗng hoặc sai hoàn toàn so với yêu cầu.
- KHÔNG dùng workflow này nếu agent chỉ đơn giản trả lời sai 1 lần (đó là vấn đề chất lượng output — xem 06.04), không phải vấn đề hành vi lặp/treo.

## Input
- Transcript đầy đủ của phiên agent bị lỗi (toàn bộ tool call + kết quả, không chỉ câu trả lời cuối).
- System prompt / agent definition gốc đang dùng.
- Mô tả kỳ vọng: agent lẽ ra phải dừng ở đâu, với kết quả gì.
- (Tuỳ chọn) So sánh với 1 lần chạy thành công trước đó (nếu có) để đối chiếu khác biệt.

## Prompt Template
```
Tôi có 1 agent bị lặp vòng / bị treo khi chạy task sau. Giúp tôi xác định nguyên nhân gốc và đề xuất fix cụ thể.

Task agent đang làm: {{mô tả task}}

System prompt / agent definition hiện tại:
{{dán nguyên văn}}

Transcript của phiên bị lỗi (tool call + kết quả, đầy đủ):
{{dán transcript, không cắt bớt phần giữa}}

Kỳ vọng đúng: agent lẽ ra phải {{mô tả hành vi đúng, vd "dừng sau khi đọc xong file X và trả về bảng tóm tắt"}}.

Yêu cầu:
1. Chỉ ra chính xác điểm agent bắt đầu lặp/treo (tool call thứ mấy, vì sao nó nghĩ chưa xong việc).
2. Phân loại nguyên nhân: (a) thiếu điều kiện dừng rõ ràng, (b) tool trả về lỗi mà agent không biết xử lý, (c) mục tiêu mơ hồ khiến agent không biết "đủ" là gì, (d) vòng lặp do tool call kết quả không thay đổi nhưng agent vẫn thử lại, (e) khác.
3. Đề xuất sửa cụ thể vào system prompt/agent definition (đưa ra đoạn text sửa, không chỉ mô tả chung chung).

Định dạng output: bảng phân tích nguyên nhân + đoạn prompt đã sửa, sẵn sàng thay thế bản cũ.
```

## Checklist
- [ ] Đã có transcript đầy đủ (không chỉ output cuối) trước khi bắt đầu debug
- [ ] Đã xác định chính xác tool call nào là điểm bắt đầu lặp/treo, không đoán chung chung
- [ ] Đã phân biệt được: lỗi do thiếu điều kiện dừng vs lỗi do tool trả về sai/lỗi mà agent không xử lý
- [ ] Đã thêm giới hạn số vòng lặp tối đa (hard limit) vào agent definition để tránh tái diễn
- [ ] Đã test lại với đúng input từng gây lỗi, xác nhận agent dừng đúng chỗ

## Expected Output
Một báo cáo ngắn gọn: nguyên nhân gốc (root cause, không phải triệu chứng), vị trí chính xác trong transcript, và đoạn system prompt/agent definition đã sửa — sẵn sàng dán thay thế bản cũ và chạy lại ngay.

## Common mistakes
- Chỉ nhìn output cuối cùng ("agent trả lời sai") mà không xem transcript đầy đủ — bỏ lỡ chuỗi tool call dẫn đến lỗi, sửa sai chỗ.
- Sửa bằng cách thêm câu "hãy cẩn thận hơn" hoặc "đừng lặp lại" vào prompt — đây là fix hời hợt, không giải quyết nguyên nhân (thường là thiếu điều kiện dừng cụ thể hoặc thiếu xử lý lỗi tool).
- Không đặt giới hạn cứng (max iterations) — ngay cả khi đã sửa prompt, vẫn nên có failsafe kỹ thuật để agent tự dừng sau N bước, tránh đốt token khi gặp case biên chưa lường trước.
- Nhầm lẫn giữa "agent lặp vì tool liên tục lỗi" và "agent lặp vì mục tiêu mơ hồ" — hai nguyên nhân cần fix khác nhau hoàn toàn (fix tool error handling vs fix rõ tiêu chí hoàn thành).
- Debug xong 1 lần rồi không test lại với case gốc đã gây lỗi — không chắc fix thực sự hiệu quả, có thể lỗi tái diễn ở lần chạy sau.

## Phiên bản Claude Code
Claude Code là môi trường phù hợp nhất để debug loại lỗi này vì bạn xem được toàn bộ tool call trực tiếp trong phiên, không cần tự chép transcript.

- Khi agent có dấu hiệu lặp vòng, dừng ngay (Ctrl+C hoặc lệnh dừng) thay vì để chạy tiếp — càng chạy lâu càng khó xác định điểm bắt đầu lỗi trong transcript dài.
- Xem lại log phiên: nếu dùng subagent, kiểm tra file log riêng của subagent đó; nếu chạy qua Agent SDK, bật `include_partial_messages`/verbose logging để thấy từng tool call.
- Thêm giới hạn cứng vào agent definition (`.claude/agents/<ten>.md`): ghi rõ trong system prompt "tối đa {{N}} lần thử lại cho cùng 1 tool call, nếu vượt quá thì dừng và báo lỗi thay vì tiếp tục".
- Dùng skill `superpowers:systematic-debugging` khi nguyên nhân không rõ ràng ngay — quy trình debug có hệ thống (lập giả thuyết, kiểm chứng từng bước) hiệu quả hơn đoán mò khi agent có hành vi phức tạp.
- Nếu lỗi lặp lại nhiều agent khác nhau, khả năng cao là mẫu system prompt gốc (template) có vấn đề chung — sửa 1 lần ở cấp template thay vì sửa từng agent riêng lẻ.

## Khi nào nên dùng Deep Research
Hầu như không cần — debug hành vi agent là vấn đề cụ thể, cần đọc transcript thật chứ không phải tổng hợp tài liệu bên ngoài. Chỉ cân nhắc Deep Research khi:
- Lỗi lặp/treo liên quan đến giới hạn kỹ thuật cụ thể của 1 công cụ/API bên thứ ba (vd rate limit, timeout behavior) mà bạn chưa hiểu rõ, cần tra cứu tài liệu chính thức của công cụ đó.
- Bạn nghi ngờ đây là vấn đề đã biết (known issue) của framework agent đang dùng và cần tìm xem cộng đồng đã có giải pháp chuẩn nào chưa trước khi tự mò.
