# Đánh giá chất lượng output của Agent (Agent Eval)

## Mục tiêu
Xây được 1 bộ eval nhỏ (5-15 test case) cho agent đang dùng, chạy tự động và cho điểm khách quan (pass/fail hoặc thang điểm), để biết chắc mỗi lần sửa prompt/agent có thực sự cải thiện hay đang làm tệ hơn — thay vì cảm tính "thấy có vẻ ổn hơn".

## Khi nào dùng
- Bạn đã có agent chạy production (theo 06.01/06.02) và chuẩn bị sửa prompt/thêm tool — cần biết thay đổi có làm hỏng case cũ không.
- Agent thỉnh thoảng ra kết quả sai nhưng bạn không có cách đo lường mức độ "thỉnh thoảng" đó là bao nhiêu %.
- Cần so sánh 2 phiên bản prompt/model khác nhau (vd Sonnet vs Opus) để quyết định dùng cái nào.
- KHÔNG cần eval bài bản nếu agent chỉ chạy 1 lần duy nhất, không tái sử dụng — review tay 1 lần là đủ.

## Input
- Danh sách 5-15 case thực tế (không phải bịa) đại diện cho các tình huống agent sẽ gặp, gồm cả case dễ và case biên (edge case).
- Với mỗi case: input, output đúng kỳ vọng (hoặc tiêu chí để đánh giá đúng/sai nếu không có 1 đáp án cố định).
- Agent/prompt hiện tại đang muốn đánh giá.
- (Tuỳ chọn) Phiên bản agent cũ để so sánh trước/sau.

## Prompt Template
```
Bạn là người đánh giá chất lượng output của 1 agent (LLM-as-judge). Nhiệm vụ: chấm điểm khách quan, không thiên vị.

Agent đang được đánh giá làm nhiệm vụ: {{mô tả nhiệm vụ agent}}

Tiêu chí chấm điểm (rubric):
1. {{tiêu chí 1, vd "đúng định dạng output yêu cầu"}} — trọng số {{%}}
2. {{tiêu chí 2, vd "không bịa thông tin không có trong input"}} — trọng số {{%}}
3. {{tiêu chí 3, vd "giải quyết đúng yêu cầu chính của input"}} — trọng số {{%}}

Dưới đây là {{N}} cặp input/output cần chấm:

Case 1:
Input: {{input case 1}}
Output của agent: {{output thực tế}}
Kỳ vọng đúng: {{đáp án đúng hoặc tiêu chí đúng}}

{{lặp lại cho các case còn lại}}

Yêu cầu:
- Chấm từng case theo rubric trên, cho điểm 0-10 và giải thích ngắn vì sao.
- Tổng hợp: % case pass (≥ ngưỡng {{X}} điểm), liệt kê case fail và nguyên nhân chung (nếu có pattern lặp lại).

Định dạng output: bảng chấm điểm từng case + tóm tắt tổng quan.
```

## Checklist
- [ ] Bộ case bao gồm cả case "dễ" (agent chắc chắn phải làm đúng) và case biên (input thiếu, input lạ, input dài)
- [ ] Mỗi case có tiêu chí đúng/sai rõ ràng, không mơ hồ (tránh rubric kiểu "trả lời hay")
- [ ] Đã chạy eval trên phiên bản hiện tại để có baseline trước khi sửa gì
- [ ] Sau khi sửa agent, chạy lại đúng bộ case cũ để so sánh — không đổi bộ test giữa chừng
- [ ] Đã xem qua ít nhất các case fail để hiểu nguyên nhân, không chỉ nhìn con số %

## Expected Output
Một bảng eval: mỗi hàng là 1 case, cột gồm input/output/điểm/lý do, cùng dòng tổng kết tỷ lệ pass. Kết quả phải đủ cụ thể để bạn quyết định "giữ nguyên agent" hay "cần sửa tiếp phần nào" mà không cần đoán.

## Common mistakes
- Chỉ test với case dễ, không có case biên — eval báo "pass 100%" nhưng agent vẫn hỏng khi gặp input thật trong production.
- Rubric mơ hồ ("output tốt", "trả lời hợp lý") khiến việc chấm điểm không nhất quán giữa các lần chạy — không dùng được để so sánh trước/sau.
- Đổi bộ test case mỗi lần eval — không so sánh được cải thiện thực sự vì đang so sánh 2 tập dữ liệu khác nhau.
- Dùng chính agent đang được đánh giá để tự chấm điểm mình (không có góc nhìn độc lập) — dễ thiên vị, bỏ sót lỗi có hệ thống.
- Chạy eval 1 lần rồi thôi, không tái sử dụng cho lần sửa tiếp theo — mất công dựng lại bộ test mỗi lần, dần dần bỏ luôn việc eval.

## Phiên bản Claude Code
Phù hợp cả 2 công cụ tuỳ quy mô: review nhanh 1 lần dùng Claude Chat với prompt trên; nếu eval chạy định kỳ (mỗi lần sửa agent) thì nên chuyển qua Claude Code để tự động hoá.

Cấu trúc project gợi ý:
```
agent-eval/
  cases/
    case-01.json          # {input, expected, criteria}
    case-02.json
    ...
  run_eval.py              # đọc từng case, gọi agent, gọi judge, ghi kết quả
  results/
    2026-08-05-baseline.md
    2026-08-06-after-fix.md
```

- Viết script `run_eval.py` dùng Claude Agent SDK: vòng lặp qua từng file trong `cases/`, gọi agent đang test lấy output, sau đó gọi Claude như "judge" chấm điểm theo rubric — tách bạch agent-được-test và judge để tránh thiên vị.
- Lưu kết quả mỗi lần chạy vào file riêng có timestamp trong `results/` — dễ diff giữa các lần để thấy cải thiện/tụt hạng theo case cụ thể (`git diff results/`).
- Có thể định nghĩa 1 subagent riêng `.claude/agents/eval-judge.md` chỉ chuyên chấm điểm, tách khỏi agent chính, đảm bảo judge không bị "nhiễm" system prompt của agent đang test.
- Chạy `npm run eval` hoặc alias tương tự để 1 lệnh chạy hết bộ case — biến việc eval thành thói quen 30 giây thay vì việc phải nhớ làm.

## Khi nào nên dùng Deep Research
Hiếm khi cần — bộ case eval nên đến từ dữ liệu thực tế của chính bạn (log agent, case đã gặp lỗi), không phải từ nghiên cứu bên ngoài. Chỉ cân nhắc Deep Research khi:
- Bạn cần chọn phương pháp/framework eval phù hợp (vd LLM-as-judge vs rule-based scoring vs human-in-loop) cho 1 loại task mới, chưa quen thuộc, và muốn so sánh ưu nhược điểm từ nhiều nguồn trước khi quyết định kiến trúc eval.
- Rubric đánh giá liên quan đến 1 lĩnh vực chuyên môn cần chuẩn tham chiếu bên ngoài (vd tiêu chuẩn ngành cụ thể) mà bạn cần tổng hợp trước khi tự đặt tiêu chí.
