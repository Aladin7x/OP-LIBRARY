# Xây dựng RAG cơ bản cho tài liệu nội bộ

## Mục tiêu
Dựng xong 1 pipeline RAG chạy được end-to-end (ingest tài liệu → embed → lưu vector store → retrieve → trả lời có trích dẫn nguồn) trong 1-2 buổi làm việc, trả lời đúng câu hỏi dựa trên tài liệu nội bộ của bạn thay vì Claude bịa từ kiến thức chung.

## Khi nào dùng
- Bạn có 1 tập tài liệu nội bộ (SOP, hợp đồng, ghi chú dự án, tài liệu sản phẩm) mà bạn hoặc AI cần tra cứu lặp lại, và dán trực tiếp vào context mỗi lần quá dài hoặc quá nhiều file.
- Tập tài liệu lớn hơn context window thực tế dùng được (vd hàng trăm file, hàng chục nghìn dòng), hoặc thay đổi liên tục nên không muốn nạp lại toàn bộ mỗi lần hỏi.
- KHÔNG dùng nếu tài liệu chỉ vài file nhỏ, dán thẳng vào Claude Chat/Project knowledge vẫn đủ context — RAG chỉ đáng công khi khối lượng tài liệu vượt quá khả năng nạp trực tiếp.

## Input
- Tập tài liệu nguồn: định dạng (PDF, Markdown, DOCX, CSV...), số lượng file, kích thước tổng.
- Quyết định trước: dùng vector store nào (đơn giản nhất cho 1 người: SQLite + extension vector, Chroma local, hoặc file-based như FAISS) — không cần hạ tầng phức tạp nếu dữ liệu dưới vài chục nghìn đoạn.
- Câu hỏi mẫu thực tế bạn sẽ hỏi hệ thống này (3-5 câu) để định hình cách chunk và retrieve.
- API key embedding model (Voyage AI được Anthropic khuyến nghị, hoặc OpenAI embeddings) nếu không tự host.

## Prompt Template
```
Bạn là {{trợ lý trả lời dựa trên tài liệu nội bộ}}. Chỉ trả lời dựa trên các đoạn tài liệu được cung cấp dưới đây — KHÔNG dùng kiến thức ngoài, KHÔNG suy đoán nếu tài liệu không đề cập.

Câu hỏi của tôi: {{câu hỏi}}

Các đoạn tài liệu liên quan (đã được retrieve từ vector store):
[Nguồn 1 - {{tên file/section}}]
{{đoạn nội dung 1}}

[Nguồn 2 - {{tên file/section}}]
{{đoạn nội dung 2}}

{{thêm các đoạn khác nếu có}}

Yêu cầu:
1. Trả lời trực tiếp câu hỏi, dựa 100% vào nội dung trên.
2. Trích dẫn rõ nguồn nào ([Nguồn X]) cho mỗi thông tin dùng trong câu trả lời.
3. Nếu thông tin trong các đoạn trên không đủ để trả lời, nói rõ "tài liệu hiện có không đề cập đến vấn đề này" — không được bịa.

Định dạng output: câu trả lời ngắn gọn + danh sách nguồn trích dẫn.
```

## Checklist
- [ ] Đã quyết định chiến lược chunk (kích thước đoạn, overlap) phù hợp với loại tài liệu (xem 07.02 để tối ưu sâu hơn)
- [ ] Đã test ingest thử với 1 subset nhỏ trước khi chạy toàn bộ tài liệu (tránh embed sai rồi phải làm lại hết)
- [ ] Prompt trả lời có ràng buộc rõ "chỉ dùng tài liệu được cung cấp" để tránh Claude bịa khi tài liệu không đủ thông tin
- [ ] Đã test với ít nhất 1 câu hỏi mà tài liệu KHÔNG có câu trả lời, xác nhận hệ thống trả lời "không biết" thay vì bịa
- [ ] Có cơ chế cập nhật tài liệu mới vào vector store mà không cần re-embed toàn bộ từ đầu

## Expected Output
Một hệ thống chạy được: nhập câu hỏi → trả về câu trả lời kèm trích dẫn nguồn cụ thể (tên file, đoạn nào). Với câu hỏi tài liệu không đề cập, hệ thống phải nói rõ thay vì bịa. Thời gian phản hồi dưới vài giây cho tập tài liệu cỡ vài trăm file.

## Common mistakes
- Chunk quá lớn (nguyên cả file dài) hoặc quá nhỏ (1-2 câu) mà không thử nghiệm — chunk sai kích thước làm retrieval trả về đoạn thiếu ngữ cảnh hoặc lẫn quá nhiều nội dung không liên quan.
- Không giữ metadata (tên file, ngày cập nhật, section) khi embed — khi retrieve được đoạn đúng nhưng không biết trích dẫn từ đâu, mất khả năng kiểm chứng.
- Bỏ qua bước re-rank hoặc lọc kết quả retrieve — lấy top-k theo similarity thô có thể trả về đoạn "giống về mặt từ ngữ" nhưng không thực sự liên quan đến câu hỏi.
- Không ràng buộc prompt "chỉ trả lời dựa trên tài liệu" — Claude có xu hướng bổ sung kiến thức chung khi tài liệu thiếu thông tin, làm mất mục đích chính của RAG (độ tin cậy).
- Xây pipeline phức tạp ngay từ đầu (nhiều tầng re-rank, hybrid search) cho tập tài liệu nhỏ — với vài trăm file, retrieval đơn giản (embedding + top-k) thường đã đủ tốt; tối ưu sớm quá mức là lãng phí thời gian.

## Phiên bản Claude Code
Đây là workflow gần như bắt buộc chạy qua Claude Code — RAG là 1 pipeline kỹ thuật cần code, không thể làm trong Claude Chat thuần.

Cấu trúc project gợi ý:
```
rag-noi-bo/
  docs/                      # tài liệu nguồn gốc
  ingest/
    chunk.py                 # đọc file, chia đoạn
    embed.py                 # gọi embedding API, lưu vào vector store
  store/
    vectors.db                # SQLite/Chroma local
  query.py                    # nhận câu hỏi, retrieve, gọi Claude trả lời
  .claude/
    agents/
      rag-answerer.md         # subagent: chỉ trả lời dựa trên context được truyền vào
```

- Lệnh khởi tạo: `pip install anthropic voyageai chromadb` (hoặc tương đương) — Voyage AI là embedding provider được Anthropic khuyến nghị chính thức, tích hợp tốt với Claude.
- Viết `ingest/chunk.py` để chia tài liệu theo cấu trúc tự nhiên (heading, đoạn văn) thay vì cắt cứng theo số ký tự — giữ ngữ nghĩa trọn vẹn hơn.
- `query.py` là script CLI đơn giản: `python query.py "câu hỏi của bạn"` → retrieve top-k → gọi Claude với prompt template ở trên → in kết quả kèm nguồn.
- Dùng Context7 MCP (`mcp__plugin_context7_context7__query-docs`) để tra cứu docs mới nhất của thư viện vector store/embedding đang dùng nếu gặp lỗi API hoặc cần cấu hình nâng cao.
- Khi tài liệu cập nhật, chạy lại `ingest/embed.py` chỉ cho file mới/thay đổi (so sánh hash hoặc timestamp) thay vì re-embed toàn bộ — tiết kiệm chi phí API embedding.

## Khi nào nên dùng Deep Research
Rất nên dùng ở giai đoạn CHỌN CÔNG CỤ trước khi bắt tay code, vì đây là quyết định kiến trúc ảnh hưởng lâu dài:
- Khi bạn chưa quyết được nên dùng vector DB nào (Chroma, Qdrant, pgvector, FAISS, SQLite-vec) cho quy mô dữ liệu và ngân sách của mình — cần so sánh chi phí, độ phức tạp vận hành, khả năng mở rộng từ nhiều nguồn cập nhật.
- Khi cần chọn embedding model (Voyage AI vs OpenAI vs open-source local) và so sánh benchmark độ chính xác/chi phí cho loại tài liệu tiếng Việt hoặc chuyên ngành cụ thể của bạn.
- Không cần Deep Research cho việc viết code ingest/query cơ bản — đó là việc code trực tiếp, dùng Context7 tra docs là đủ.
