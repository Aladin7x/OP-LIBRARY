# Đánh giá và cải thiện Prompt (Prompt Evaluation Loop)

## Mục tiêu
Có 1 vòng lặp đánh giá - cải thiện có hệ thống cho 1 prompt quan trọng đang dùng thường xuyên, để sau 3-5 vòng lặp output ổn định và đúng ý hơn rõ rệt — thay vì sửa ngẫu hứng mỗi khi thấy kết quả không ưng.

## Khi nào dùng
- 1 prompt đang dùng thường xuyên nhưng output không ổn định — lúc tốt lúc tệ dù input tương tự
- Chuẩn bị đưa 1 prompt vào dùng lâu dài (làm template ở 14.01, làm skill, hoặc đưa vào automation) nên cần test kỹ trước khi cố định
- Vừa nhận ra 1 lỗi lặp lại nhiều lần từ cùng 1 prompt (vd: luôn thiếu 1 mục, luôn hiểu sai 1 loại yêu cầu)
- KHÔNG cần vòng lặp đầy đủ cho 1 prompt one-off chỉ dùng đúng 1 lần rồi bỏ

## Input
- Prompt hiện tại đang dùng
- 3-5 output thực tế đã nhận được từ prompt đó — cả output tốt lẫn output chưa tốt, không chỉ chọn lọc trường hợp xấu nhất
- Tiêu chí bạn coi là "output tốt" cho việc này, viết ra thành chữ càng cụ thể càng tốt (không chỉ "thấy ổn là được")

## Prompt Template
```
Bạn là reviewer giúp tôi đánh giá và cải thiện 1 prompt tôi đang dùng thường xuyên. Đừng chỉ khen chung chung — chỉ ra cụ thể điểm mơ hồ và đề xuất cách sửa rõ ràng.

Prompt hiện tại:
{{dán nguyên văn prompt đang dùng}}

Tiêu chí tôi coi là output tốt cho việc này:
{{liệt kê cụ thể, vd: "đủ 5 mục, mỗi mục dưới 100 từ, không lặp ý giữa các mục, giọng văn trực tiếp không sáo rỗng"}}

3-5 output thực tế đã nhận được (kèm input tương ứng nếu có):
{{dán output 1, output 2, output 3...}}

Yêu cầu:
1. So sánh từng output với tiêu chí tôi đưa ra — chỉ rõ output nào đạt, output nào không đạt và vì sao.
2. Chỉ ra điểm mơ hồ/thiếu ràng buộc trong prompt hiện tại là nguyên nhân khiến output không ổn định.
3. Đề xuất 1 bản prompt v2 đã sửa các điểm mơ hồ đó — chỉ sửa những gì thực sự cần, không viết lại toàn bộ nếu không cần thiết.
4. Giải thích ngắn gọn từng thay đổi trong v2 nhằm giải quyết vấn đề gì cụ thể.

Định dạng output: bảng so sánh output vs tiêu chí, sau đó là bản prompt v2 trong code block, kèm danh sách giải thích thay đổi.
```

## Checklist
- [ ] Đã thu thập tối thiểu 3 output thực tế trước khi đánh giá, không đánh giá dựa trên 1 lần chạy duy nhất
- [ ] Đã viết rõ tiêu chí "output tốt" bằng chữ trước khi nhờ Claude đánh giá, tránh đánh giá cảm tính
- [ ] Đã test bản prompt mới với cùng input cũ để so sánh trực tiếp trước/sau
- [ ] Đã lưu lại lịch sử các phiên bản prompt (v1, v2, v3...) để biết mình đã thử gì rồi
- [ ] Đã dừng vòng lặp khi output đạt tiêu chí, thay vì tiếp tục tối ưu vô thời hạn

## Expected Output
1 bảng so sánh prompt cũ và mới (điểm mơ hồ đã sửa, ví dụ output trước/sau), kèm 1 bản prompt v2 (hoặc v3 nếu đã qua nhiều vòng) rõ ràng hơn, và ghi chú lý do cho từng thay đổi. Kết quả tốt là bạn hiểu được chính xác vì sao prompt cũ không ổn định, không chỉ có 1 bản prompt mới mà không rõ lý do.

## Common mistakes
- Đánh giá dựa trên cảm giác "thấy ổn hơn" thay vì so sánh output cụ thể trước/sau với cùng 1 input — dễ tự đánh lừa mình rằng đã cải thiện
- Sửa quá nhiều thứ cùng lúc trong 1 vòng lặp, nên không biết thay đổi nào thực sự tạo ra khác biệt và thay đổi nào không cần thiết
- Không lưu lại phiên bản cũ, mất khả năng so sánh hoặc rollback nếu bản mới lại tệ hơn bản trước
- Tối ưu prompt quá khớp cho 1 trường hợp cá biệt, khiến nó kém tổng quát hơn cho các trường hợp khác vẫn hay gặp
- Dừng lại sau 1 vòng vì nghĩ "tệ mãi vẫn thế", trong khi vấn đề thực ra nằm ở tiêu chí đánh giá chưa đủ rõ, không phải bản thân prompt

## Phiên bản Claude Code
Workflow này chủ yếu dùng Claude Chat cho phần tư duy đánh giá — cần đọc và phản biện qua lại, không phải thao tác file lặp lại. Nếu prompt đang đánh giá được dùng trong 1 project code cụ thể (ví dụ prompt cho 1 subagent hoặc 1 skill riêng), nên lưu lịch sử phiên bản ngay trong git thay vì lưu thủ công nhiều file rời: mỗi lần sửa prompt trong file `.md` là 1 commit riêng, dùng `git log` và `git diff` để xem lại đã thay đổi gì giữa các vòng lặp.

## Khi nào nên dùng Deep Research
Ít cần — đây là vòng lặp dựa trên dữ liệu output thật của chính bạn, không cần tổng hợp nguồn bên ngoài để đánh giá. Có thể hữu ích nếu bạn muốn tham khảo các kỹ thuật prompt engineering mới trước khi bắt đầu vòng sửa (ví dụ cách cấu trúc few-shot examples hiệu quả hơn), nhưng đây là bước bổ sung tuỳ chọn, không phải phần bắt buộc của vòng lặp đánh giá cốt lõi.
