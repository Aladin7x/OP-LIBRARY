# Viết SQL query từ yêu cầu ngôn ngữ tự nhiên

## Mục tiêu
Có được câu SQL đúng, chạy được ngay lần đầu (hoặc sau 1 lần sửa nhỏ) cho câu hỏi kinh doanh cụ thể, thay vì tự nhớ syntax JOIN/window function mất 10-15 phút tra cứu mỗi lần.

## Khi nào dùng
- Cần truy vấn dữ liệu từ database (không phải file CSV rời — xem 08.01 cho trường hợp đó) để trả lời câu hỏi cụ thể.
- Câu query cần logic phức tạp hơn SELECT đơn giản (JOIN nhiều bảng, window function, subquery, aggregate theo điều kiện) mà bạn không nhớ syntax chính xác.
- Cần viết nhanh nhiều query biến thể (thay đổi điều kiện lọc/nhóm) cho cùng 1 câu hỏi gốc.
- KHÔNG dùng nếu query đơn giản bạn đã thuộc lòng — tự viết nhanh hơn hỏi.

## Input
- Schema database liên quan: tên bảng, tên cột, kiểu dữ liệu, quan hệ khoá ngoại (không cần toàn bộ schema, chỉ phần liên quan câu hỏi).
- Loại database đang dùng (PostgreSQL, MySQL, SQLite, BigQuery...) — syntax khác nhau giữa các hệ.
- Câu hỏi kinh doanh cụ thể cần trả lời bằng query.
- (Tuỳ chọn) Dữ liệu mẫu 2-3 dòng để Claude hiểu định dạng giá trị thực tế (vd date format, cách lưu trạng thái).

## Prompt Template
```
Bạn là chuyên gia SQL. Viết query cho {{loại database, vd "PostgreSQL"}} trả lời câu hỏi sau.

Schema liên quan:
{{tên bảng 1}} ({{cột 1}}: {{kiểu}}, {{cột 2}}: {{kiểu}}, ...)
{{tên bảng 2}} ({{cột 1}}: {{kiểu}}, ...) — quan hệ: {{mô tả khoá ngoại nếu có}}

Dữ liệu mẫu (để hiểu định dạng thực tế):
{{2-3 dòng mẫu nếu có}}

Câu hỏi cần trả lời: {{câu hỏi cụ thể, vd "top 10 khách hàng có tổng giá trị đơn hàng cao nhất trong quý 2/2026, loại trừ đơn đã huỷ"}}

Yêu cầu:
1. Viết query đầy đủ, chạy được ngay, đúng syntax {{loại database}}.
2. Giải thích ngắn gọn logic từng phần (JOIN gì với gì, điều kiện lọc nào).
3. Nếu câu hỏi có thể hiểu theo nhiều cách, nêu rõ giả định đã chọn (vd "giả định 'giá trị đơn hàng' là tổng sau giảm giá, trước thuế").

Định dạng output: code block SQL + giải thích ngắn + giả định (nếu có).
```

## Checklist
- [ ] Đã cung cấp đúng tên bảng/cột thực tế (không phải đoán) — sai tên cột là lỗi phổ biến nhất khiến query không chạy
- [ ] Đã nêu rõ loại database vì syntax window function, date function khác nhau đáng kể giữa Postgres/MySQL/SQLite/BigQuery
- [ ] Đã kiểm tra logic loại trừ (đơn huỷ, dữ liệu test, soft-delete) được áp dụng đúng, không bị bỏ sót
- [ ] Đã chạy thử query trên tập dữ liệu nhỏ/staging trước khi chạy trên production, đặc biệt với query có JOIN phức tạp
- [ ] Đã đối chiếu giả định Claude nêu ra (vd cách tính "giá trị đơn hàng") có đúng ý bạn muốn hỏi không

## Expected Output
Một câu SQL hoàn chỉnh, chạy được ngay (hoặc chỉ cần sửa tên bảng/schema cho khớp môi trường thật), kèm giải thích logic đủ để bạn tự kiểm tra được là query có đúng ý câu hỏi hay không trước khi chạy trên dữ liệu thật.

## Common mistakes
- Không cung cấp schema thật, để Claude tự đoán tên cột — query trông hợp lý về logic nhưng sai tên bảng/cột, không chạy được.
- Quên nói loại database — Claude mặc định dùng syntax phổ biến (thường giống PostgreSQL) trong khi bạn dùng MySQL/SQLite, dẫn đến lỗi function không tồn tại (vd `DATE_TRUNC` chỉ có ở Postgres).
- Không kiểm tra điều kiện loại trừ dữ liệu rác (đơn huỷ, soft-delete `deleted_at IS NULL`) — kết quả tính sai mà nhìn qua vẫn "hợp lý".
- Chạy thẳng query UPDATE/DELETE do Claude viết lên production mà không review kỹ hoặc test trên bản sao trước — rủi ro mất dữ liệu nếu điều kiện WHERE sai hoặc thiếu.
- Câu hỏi mơ hồ về định nghĩa (vd "doanh thu" có tính hoàn tiền không, "khách hàng active" nghĩa là gì) khiến Claude tự chọn giả định có thể không khớp ý bạn — luôn đọc phần "giả định" Claude nêu ra trước khi tin kết quả.

## Phiên bản Claude Code
Phù hợp Claude Code khi cần chạy query trực tiếp lên database thật, lặp lại nhiều lần, hoặc lưu thành thư viện query dùng lại.

Cấu trúc project gợi ý:
```
db-queries/
  schema.sql                   # dump schema tham chiếu, cập nhật định kỳ
  queries/
    top-customers-q2.sql
    revenue-by-month.sql
  .claude/
    agents/
      sql-writer.md              # subagent: tools gồm Read (schema.sql) + Bash (chạy query qua CLI DB)
```

- Nếu có MCP server kết nối trực tiếp database (vd BigQuery, Postgres MCP), dùng nó để Claude Code tự chạy thử query và xác nhận kết quả thay vì bạn phải copy-paste qua tool khác.
- Lưu `schema.sql` (output của `pg_dump --schema-only` hoặc tương đương) trong project để Claude luôn có schema chính xác thay vì bạn phải gõ tay mỗi lần hỏi.
- Với query phức tạp/quan trọng, yêu cầu Claude Code chạy thử trên `EXPLAIN ANALYZE` trước để kiểm tra performance, đặc biệt nếu bảng có hàng triệu dòng — tránh query chạy chậm hoặc khoá bảng khi chạy trên production.
- Không bao giờ để Claude Code tự động chạy query UPDATE/DELETE/DROP lên production mà không có bước bạn tự confirm — luôn review nội dung câu lệnh trước khi cho phép chạy khi có write access thật.

## Khi nào nên dùng Deep Research
Hiếm khi cần cho việc viết query trên schema đã biết — đây là việc dịch yêu cầu sang syntax, dùng Context7 để tra docs SQL dialect cụ thể nếu gặp function lạ là đủ. Cân nhắc Deep Research khi:
- Cần thiết kế lại schema hoặc chọn công cụ database mới (vd chuyển từ SQLite sang Postgres/BigQuery cho quy mô lớn hơn) và cần so sánh đánh đổi giữa các lựa chọn.
- Query cần tối ưu hiệu năng phức tạp (indexing strategy, partitioning) cho bảng cực lớn, cần tổng hợp best practice cụ thể theo loại database đang dùng.
