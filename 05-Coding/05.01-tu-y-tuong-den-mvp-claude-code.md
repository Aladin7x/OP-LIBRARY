# Từ ý tưởng đến MVP (Claude Code end-to-end)

## Mục tiêu
Đi từ 1 ý tưởng sản phẩm (mô tả bằng lời) đến 1 MVP chạy được, có test cơ bản và deploy thử, trong 1-3 ngày làm việc thay vì 2-3 tuần tự code từ đầu.

## Khi nào dùng
- Bạn có ý tưởng sản phẩm/tính năng rõ ràng, biết muốn giải quyết vấn đề gì, nhưng chưa viết dòng code nào.
- Cần dựng nhanh 1 bản demo để test ý tưởng với khách hàng/thị trường trước khi đầu tư sâu.
- Không dùng workflow này khi ý tưởng còn mơ hồ — quay lại workflow 03.02 (brainstorm) hoặc 09.01 (business plan) để làm rõ trước, tránh Claude Code build sai thứ ngay từ đầu.

## Input
- Mô tả sản phẩm: vấn đề giải quyết, người dùng mục tiêu, 3-5 tính năng cốt lõi (không phải wishlist đầy đủ).
- Stack công nghệ ưu tiên (nếu có gu riêng), hoặc để Claude đề xuất dựa trên quy mô dự án.
- Ràng buộc: deadline, ngân sách hosting, có cần auth/database ngay từ đầu không.
- (Tuỳ chọn) Wireframe/mô tả UI thô, hoặc ví dụ sản phẩm tương tự để tham khảo.

## Prompt Template
```
Tôi muốn xây MVP cho ý tưởng sau. Đóng vai kỹ sư phần mềm senior, làm việc trực tiếp với tôi (founder kỹ thuật một mình).

Ý tưởng: {{mô tả sản phẩm, vấn đề giải quyết}}
Người dùng mục tiêu: {{ai sẽ dùng}}
Tính năng cốt lõi cho MVP (chỉ những gì bắt buộc để test ý tưởng): {{liệt kê 3-5 tính năng}}
Stack ưu tiên: {{ngôn ngữ/framework, hoặc "bạn đề xuất phù hợp nhất"}}
Ràng buộc: {{deadline, hosting, database...}}

Yêu cầu:
1. Trước khi code, đề xuất kiến trúc tổng thể (không cần chi tiết) và danh sách các bước theo thứ tự ưu tiên.
2. Vào plan mode để tôi duyệt kế hoạch trước khi bắt đầu implement.
3. Build theo từng bước nhỏ, có thể chạy/test được sau mỗi bước — không viết toàn bộ codebase rồi mới test.
4. Viết test cơ bản cho logic quan trọng (không cần coverage 100%, MVP không cần).

Bắt đầu bằng việc hỏi tôi bất kỳ thông tin nào còn thiếu trước khi lên kế hoạch.
```

## Checklist
- [ ] Duyệt kế hoạch (plan mode) trước khi để Claude Code bắt đầu viết code — đừng để chạy tự do ngay từ đầu.
- [ ] Sau mỗi milestone, tự chạy app thử tay (không chỉ tin vào "tests pass").
- [ ] Kiểm tra Claude không tự thêm tính năng ngoài phạm vi MVP đã chốt (scope creep).
- [ ] Có ít nhất 1 file README/setup instructions để bạn (hoặc tương lai) chạy lại project được.
- [ ] Commit code theo từng milestone nhỏ, không dồn 1 commit khổng lồ cuối cùng.
- [ ] Kiểm tra biến môi trường/secrets không bị commit nhầm vào git.

## Expected Output
1 repo chạy được local, có cấu trúc rõ ràng, README hướng dẫn setup, test cơ bản cho phần logic quan trọng, và ít nhất đã deploy thử lên 1 môi trường (Vercel/Railway/VPS...). Không kỳ vọng code hoàn hảo production-grade — MVP nghĩa là "đủ tốt để test giả thuyết", không phải "đủ tốt để scale".

## Common mistakes
- Nhảy thẳng vào code mà không dùng plan mode — Claude Code sẽ tự quyết định kiến trúc theo cách nó nghĩ là hợp lý, có thể không khớp ràng buộc thực tế của bạn.
- Liệt kê quá nhiều tính năng "cốt lõi" — MVP thật sự chỉ nên có 3-5 tính năng, nhiều hơn là đang xây sản phẩm đầy đủ chứ không phải MVP.
- Không test tay sau mỗi bước, đợi đến cuối mới chạy thử — lỗi tích luỹ khó tìm ra nguyên nhân gốc.
- Để Claude Code tự chọn stack không hợp với kỹ năng bạn có — nếu bạn phải maintain sau này, stack cần bạn đọc hiểu được, không chỉ tối ưu về mặt kỹ thuật.
- Quên hỏi về giới hạn ngân sách/hosting trước — Claude có thể đề xuất kiến trúc cần nhiều service trả phí không cần thiết cho MVP.

## Phiên bản Claude Code
Đây là workflow Claude Code thuần, không có phiên bản Claude Chat tương đương (Claude Chat không tạo và chạy được codebase thật).

Quy trình cụ thể:
1. Tạo thư mục project, `cd` vào đó, chạy `claude` để mở phiên làm việc.
2. Mở đầu bằng plan mode (`Shift+Tab` để chuyển chế độ, hoặc gõ "vào plan mode trước khi code") — để Claude Code đề xuất kiến trúc và roadmap trước khi đụng vào file nào.
3. Duyệt plan, yêu cầu chỉnh nếu cần (vd "bỏ auth ở bản đầu, thêm sau"), rồi mới cho phép implement.
4. Trong lúc build, để Claude Code tự dùng TodoWrite quản lý danh sách việc (tạo model → API route → UI → test) — bạn theo dõi tiến độ qua danh sách này thay vì hỏi lại "đang làm gì".
5. Cấu trúc thư mục gợi ý cho project nhỏ: `/src`, `/tests`, `README.md`, `.env.example` (không commit `.env` thật).
6. Sau mỗi milestone, chạy lệnh test thật (vd `npm test`, `pytest`) — yêu cầu Claude Code tự chạy và dán kết quả, không chỉ báo "đã viết test".
7. Ví dụ lệnh mẫu trong 1 phiên: sau khi plan được duyệt, gõ "Implement bước 1 trong plan, chạy test sau khi xong, báo lại kết quả trước khi qua bước 2."
8. Nếu project đủ lớn (nhiều module độc lập: backend + frontend + worker), cân nhắc dùng subagent riêng cho từng phần qua Agent tool thay vì để 1 phiên làm hết tuần tự.

## Khi nào nên dùng Deep Research
Hiếm khi cần cho việc build MVP nói chung — Claude Code đã có kiến thức đủ về các stack phổ biến. Ngoại lệ: khi bạn chọn 1 thư viện/API mới, ít phổ biến, hoặc vừa ra bản lớn gần đây (breaking changes) — lúc đó nên tra cứu tài liệu chính thức trực tiếp (dùng Context7 hoặc đọc docs) trước khi để Claude Code implement, để tránh code dựa trên phiên bản API cũ đã lỗi thời trong dữ liệu huấn luyện.
