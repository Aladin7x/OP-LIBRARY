# Debug lỗi production với log thực tế

## Mục tiêu
Tìm ra root cause của 1 lỗi production và có bản fix đã test trong 30-90 phút (thay vì đoán mò và vá tạm), dựa trên log/stack trace thật chứ không phải mô tả chung chung.

## Khi nào dùng
- Có lỗi thật đang xảy ra trên production, có log/error message/stack trace cụ thể.
- Lỗi khó tái hiện local, cần suy luận từ dữ liệu log thực tế.
- Không dùng workflow này khi chưa có log/error cụ thể trong tay — lúc đó việc đầu tiên là thêm logging vào chỗ nghi ngờ, chưa phải debug.

## Input
- Log lỗi/stack trace đầy đủ (copy nguyên văn, không tóm tắt lại — mất chi tiết là mất manh mối).
- Đoạn code liên quan (file, hàm, hoặc để Claude Code tự đọc trong repo).
- Điều kiện xảy ra lỗi: tần suất, có tái hiện được không, xảy ra từ khi nào (liên quan đến deploy gần đây không).
- (Tuỳ chọn) Log của request/transaction thành công tương tự để so sánh.

## Prompt Template
```
Tôi có lỗi production cần tìm root cause, không muốn vá tạm (band-aid fix).

Log/stack trace:
{{dán nguyên văn log lỗi}}

Bối cảnh:
- Lỗi xảy ra: {{tần suất, có tái hiện local được không}}
- Bắt đầu xuất hiện từ: {{thời điểm, có trùng với deploy/thay đổi gần đây không}}
- File/module nghi ngờ liên quan: {{đường dẫn nếu biết}}

Yêu cầu:
1. Đọc kỹ log trước, liệt kê các giả thuyết có thể gây lỗi (đừng kết luận vội).
2. Với mỗi giả thuyết, kiểm tra trong code thật xem có khớp không, loại dần thay vì đoán 1 giả thuyết rồi sửa ngay.
3. Khi xác định root cause, giải thích rõ tại sao lỗi này xảy ra và tại sao chỉ giờ mới xuất hiện.
4. Đề xuất fix, kèm test để đảm bảo lỗi này không lặp lại (regression test).

Không tự ý sửa code cho đến khi tôi xác nhận root cause đúng.
```

## Checklist
- [ ] Root cause được giải thích rõ ràng, không phải "có thể do X" mơ hồ.
- [ ] Có xác nhận tại sao lỗi chỉ xảy ra bây giờ (thay đổi gần đây, edge case, race condition...).
- [ ] Fix đi kèm test tái hiện được lỗi gốc (test fail trước khi fix, pass sau khi fix).
- [ ] Kiểm tra fix không phá vỡ luồng khác — chạy full test suite, không chỉ test mới viết.
- [ ] Xem lại có cần thêm logging/monitoring ở chỗ này để bắt lỗi tương tự nhanh hơn lần sau không.

## Expected Output
1 bản giải thích root cause rõ ràng (2-4 câu, ai đọc cũng hiểu tại sao lỗi xảy ra), kèm diff code fix cụ thể và ít nhất 1 test mới tái hiện được lỗi gốc rồi xác nhận đã pass sau khi fix. Không chấp nhận output kiểu "thêm try/catch để tránh crash" mà không giải thích được nguyên nhân gốc.

## Common mistakes
- Dán tóm tắt lỗi thay vì log nguyên văn — mất chi tiết quan trọng (timestamp, request ID, giá trị biến) mà root cause thường nằm ở đó.
- Chấp nhận fix đầu tiên Claude đề xuất mà không hỏi "tại sao lỗi này xảy ra" — dễ dính band-aid fix (vd thêm null check) che giấu vấn đề sâu hơn.
- Không yêu cầu test regression — fix xong nhưng không có gì đảm bảo lỗi không quay lại ở lần deploy sau.
- Bỏ qua bước kiểm tra "trùng thời điểm với deploy nào" — đây thường là manh mối nhanh nhất để tìm root cause, hay bị bỏ qua vì muốn nhảy thẳng vào code.
- Sửa nhiều chỗ cùng lúc khi không chắc root cause — nếu lỗi hết, bạn không biết chỗ nào thực sự giải quyết vấn đề.

## Phiên bản Claude Code
Đây là workflow Claude Code thuần — cần đọc trực tiếp trong codebase và chạy lệnh, Claude Chat không làm được việc này hiệu quả.

Quy trình cụ thể:
1. Trong thư mục project, chạy `claude`, dán log lỗi trực tiếp vào prompt (không cần file riêng nếu log ngắn; nếu log dài, lưu vào file `debug/incident-{{ngày}}.log` rồi trỏ Claude Code đọc file đó).
2. Dùng systematic-debugging: yêu cầu Claude Code liệt kê giả thuyết trước, dùng Grep/Read để kiểm tra từng giả thuyết trong code thật, thay vì đoán và sửa ngay — nếu có skill `superpowers:systematic-debugging` trong hệ thống, đây đúng lúc để dùng.
3. Nếu cần tái hiện lỗi local, để Claude Code viết 1 test case fail trước (TDD ngược: viết test tái hiện lỗi → xác nhận fail đúng lỗi → fix → xác nhận test pass).
4. Lệnh mẫu: `claude "Đọc log trong debug/incident-2026-08-05.log, đọc file src/api/checkout.ts liên quan, liệt kê giả thuyết trước khi kết luận root cause."`
5. Sau khi có fix, chạy full test suite thật (`npm test` / `pytest -x`) qua Bash để xác nhận không phá vỡ chỗ khác — đừng chỉ tin báo cáo bằng lời.
6. Commit fix kèm message mô tả root cause (không chỉ "fix bug"), để lần sau grep log dễ tìm lại lý do.

## Khi nào nên dùng Deep Research
Hiếm khi cần cho debug thông thường. Ngoại lệ: lỗi liên quan đến hành vi lạ của 1 thư viện/API bên thứ ba (vd breaking change trong SDK, bug đã biết của 1 phiên bản cụ thể) — lúc đó tra cứu changelog/issue tracker chính thức của thư viện đó (qua Context7 hoặc WebSearch) sẽ nhanh hơn đoán từ log, vì đây là thông tin cần cập nhật mà kiến thức nền của Claude có thể không có.
