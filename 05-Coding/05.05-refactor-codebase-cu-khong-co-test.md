# Refactor codebase cũ không có test

## Mục tiêu
Refactor an toàn 1 phần codebase cũ (không có test bảo vệ) mà không làm gãy hành vi hiện tại — đo bằng việc có test bao phủ hành vi cũ trước khi đổi cấu trúc, và hệ thống chạy đúng như trước sau refactor.

## Khi nào dùng
- Codebase cũ, không có test, cần sửa/mở rộng nhưng sợ đụng vào là gãy chỗ khác.
- Code đã "smell" rõ (hàm quá dài, logic trùng lặp, khó đọc) và đang cản trở việc thêm tính năng mới.
- Không dùng workflow này nếu mục tiêu là viết lại từ đầu (rewrite) — đó là quyết định khác, rủi ro cao hơn nhiều, cần cân nhắc riêng, không phải "refactor".

## Input
- Phần code cần refactor (file/module cụ thể, không nên refactor toàn bộ codebase cùng lúc).
- Lý do cần refactor: khó thêm tính năng gì, hay bug lặp lại ở đâu.
- Xác nhận: có cách nào chạy thử/quan sát hành vi hiện tại không (staging, log, hoặc chạy tay).
- (Tuỳ chọn) Ràng buộc không được đổi: API public, tên hàm được gọi từ nơi khác, format dữ liệu output.

## Prompt Template
```
Bạn là kỹ sư refactor, nguyên tắc quan trọng nhất: KHÔNG đổi hành vi bên ngoài, chỉ đổi cấu trúc bên trong.

Code cần refactor:
{{dán code hoặc đường dẫn file/module}}

Lý do refactor: {{khó thêm tính năng gì, code smell cụ thể}}
Ràng buộc không được đổi: {{API public, tên hàm, format output...}}

Yêu cầu — làm theo đúng thứ tự, không nhảy bước:
1. Trước tiên, viết "characterization tests" — test ghi lại hành vi HIỆN TẠI của code (kể cả nếu hành vi đó hơi kỳ lạ), để có lưới an toàn trước khi đổi gì.
2. Chạy test này, xác nhận pass với code hiện tại (đây là baseline).
3. Refactor từng bước nhỏ (đổi tên, tách hàm, gộp logic trùng) — sau MỖI bước nhỏ, chạy lại characterization test để xác nhận vẫn pass.
4. Không refactor nhiều thứ cùng lúc trong 1 bước — nếu test fail, phải biết ngay bước nào gây ra.
5. Sau khi xong, tổng kết những gì đã đổi cấu trúc và xác nhận hành vi bên ngoài không đổi.
```

## Checklist
- [ ] Characterization test được viết và pass với code CŨ trước khi đổi bất cứ gì.
- [ ] Mỗi bước refactor nhỏ, có chạy test ngay sau đó — không dồn nhiều thay đổi rồi mới test 1 lần.
- [ ] Kiểm tra ràng buộc "không được đổi" (API, tên hàm) thực sự không đổi.
- [ ] Nếu phát hiện bug có sẵn trong code cũ lúc refactor, KHÔNG tự sửa luôn — ghi lại riêng, xử lý như 1 việc khác (refactor và fix bug là 2 việc khác nhau).
- [ ] Sau khi xong, xác nhận không chỉ test pass mà còn chạy thử tay ở môi trường gần giống thật nhất có thể.

## Expected Output
Code có cấu trúc rõ ràng hơn (hàm ngắn hơn, đặt tên tốt hơn, giảm trùng lặp), đi kèm bộ characterization test chứng minh hành vi bên ngoài không đổi so với trước. Có 1 bản tóm tắt ngắn liệt kê những gì đã đổi cấu trúc (không phải hành vi) để bạn review lại logic thay đổi có hợp lý không.

## Common mistakes
- Refactor và fix bug cùng lúc trong 1 bước — khi có gì sai, không biết là do refactor gãy hay do bug cũ lộ ra, rất khó debug ngược lại.
- Bỏ qua bước viết characterization test vì "code đơn giản mà" — đây là nguyên nhân phổ biến nhất khiến refactor "an toàn" hoá ra làm gãy 1 case hiếm không ai nhớ tới.
- Refactor cả 1 module lớn trong 1 lần thay vì chia nhỏ từng bước có thể verify — khi có lỗi, phạm vi nghi ngờ quá rộng, mất nhiều thời gian tìm ra bước nào gây lỗi.
- Đổi luôn API public/tên hàm được gọi từ chỗ khác mà không kiểm tra hết nơi gọi tới — gãy chỗ khác trong hệ thống mà không hay biết ngay lập tức.
- Tin tưởng characterization test 100% dù nó chỉ cover được hành vi mà bạn nghĩ ra để test — với code thực sự phức tạp, vẫn nên chạy thử tay ở case quan trọng nhất, không chỉ dựa vào test tự động.

## Phiên bản Claude Code
Đây là workflow Claude Code thuần, cần khả năng đọc/sửa nhiều file và chạy test lặp lại liên tục.

Quy trình cụ thể:
1. Trong thư mục repo, tạo branch riêng trước khi bắt đầu: `git checkout -b refactor/{{ten-module}}` — refactor luôn cần rollback dễ dàng nếu sai.
2. Chạy `claude`, vào plan mode trước để Claude Code đề xuất các bước refactor nhỏ theo thứ tự, bạn duyệt trước khi thực thi từng bước.
3. Lệnh mẫu bước 1: `claude "Đọc src/services/order.ts, viết characterization test bao phủ hành vi hiện tại (kể cả case kỳ lạ), chạy test xác nhận pass với code hiện tại trước khi tôi cho phép đổi gì."`
4. Sau khi có baseline test pass, yêu cầu Claude Code refactor từng bước nhỏ, mỗi bước tự chạy lại test suite qua Bash và báo cáo pass/fail trước khi qua bước tiếp — dùng TodoWrite để liệt kê từng bước refactor nhỏ và đánh dấu hoàn thành lần lượt.
5. Commit sau mỗi bước nhỏ pass test (không dồn 1 commit lớn cuối) — nếu bước sau làm gãy gì, dễ `git revert` đúng bước đó thay vì mất hết công sức.
6. Nếu module quá lớn/phức tạp, cân nhắc dùng subagent riêng cho từng phần độc lập (vd 1 subagent lo characterization test, 1 subagent khác lo refactor) để giữ context sạch cho từng việc.

## Khi nào nên dùng Deep Research
Hiếm khi cần — refactor dựa trên nguyên tắc kỹ thuật chung (giảm trùng lặp, tách trách nhiệm), không cần nguồn ngoài. Ngoại lệ: khi refactor liên quan đến việc đổi sang 1 pattern/thư viện mới hoàn toàn (vd chuyển từ callback sang async/await ở quy mô lớn, hoặc áp dụng 1 kiến trúc mới bạn chưa quen) — lúc đó nên tra cứu best practice và pitfall thường gặp của pattern đó trước khi bắt tay refactor toàn bộ.
