# Code review trước khi merge

## Mục tiêu
Có 1 vòng review độc lập, nghiêm túc cho 1 branch/PR trước khi merge vào main, phát hiện được ít nhất các lỗi logic/bảo mật/edge-case rõ ràng, trong 10-20 phút — thay thế việc tự đọc lại code của chính mình (vốn dễ bỏ sót vì đã quen mắt).

## Khi nào dùng
- Trước khi merge bất kỳ branch nào vào main, đặc biệt khi làm một mình không có đồng nghiệp review chéo.
- Sau khi Claude Code (hoặc bạn) vừa implement xong 1 tính năng/fix và muốn 1 góc nhìn "mới" trước khi chốt.
- Không dùng workflow này thay cho test tự động — review giúp bắt lỗi logic/thiết kế, không thay thế được việc chạy test thật (xem workflow 05.04).

## Input
- Diff/PR cần review (Claude Code có thể tự đọc qua `git diff` nếu chạy trong repo).
- Bối cảnh: tính năng này làm gì, có ràng buộc đặc biệt gì (performance, bảo mật, tương thích ngược).
- Mức độ nghiêm ngặt mong muốn (MVP nhanh vs. code chạm vào production quan trọng).
- (Tuỳ chọn) Coding convention/style guide riêng của project nếu có.

## Prompt Template
```
Bạn là senior engineer làm code review độc lập, không phải người viết code này — hãy nghiêm khắc như review code của người lạ, không nương tay vì "chắc tác giả biết mình đang làm gì".

Diff cần review:
{{dán git diff, hoặc yêu cầu Claude Code tự chạy git diff main...HEAD}}

Bối cảnh: {{tính năng này làm gì, ràng buộc đặc biệt}}
Mức độ nghiêm ngặt: {{MVP nhanh / production quan trọng}}

Yêu cầu review theo thứ tự:
1. Đúng logic không — có case nào input hợp lệ nhưng code xử lý sai không.
2. Edge case nào chưa xử lý (input rỗng, null, số âm, timeout, race condition).
3. Vấn đề bảo mật (injection, secrets lộ ra, thiếu validate input từ user).
4. Có đoạn nào phức tạp không cần thiết, có thể đơn giản hoá không.
5. Test có đủ cover các case quan trọng không (không cần 100%, cần đúng chỗ rủi ro).

Phân loại mỗi phát hiện: [BẮT BUỘC SỬA] / [NÊN SỬA] / [Ý KIẾN, tuỳ chọn]. Không phát hiện gì thì nói rõ "không thấy vấn đề" thay vì bịa ra lỗi để có gì đó báo cáo.
```

## Checklist
- [ ] Đọc hết các mục [BẮT BUỘC SỬA] trước, xử lý hết mới merge.
- [ ] Với mỗi [NÊN SỬA], tự quyết định sửa ngay hay ghi lại làm sau (đừng để trôi luôn).
- [ ] Kiểm tra chéo: chạy thử ít nhất 1 edge case mà review vừa chỉ ra, xác nhận đúng là có vấn đề.
- [ ] Đảm bảo review có đọc thật (grep/read code liên quan), không chỉ đọc diff bề mặt.
- [ ] Sau khi sửa theo review, chạy lại test suite trước khi merge.

## Expected Output
1 danh sách phát hiện có phân loại rõ ràng (bắt buộc/nên/ý kiến), mỗi phát hiện trỏ đúng dòng/file và giải thích tại sao là vấn đề — không phải nhận xét chung chung kiểu "code có vẻ ổn". Nếu diff nhỏ và sạch, output ngắn (vài dòng) là bình thường — không cần review "thổi phồng" ra vấn đề để có nội dung báo cáo.

## Common mistakes
- Để chính Claude Code (agent vừa viết code) tự review code của chính nó trong cùng 1 phiên — dễ bị thiên vị, xác nhận lại logic nó vừa nghĩ ra thay vì phản biện. Tốt hơn: mở phiên/agent review riêng, hoặc ít nhất yêu cầu rõ "đóng vai reviewer độc lập, phản biện nghiêm khắc".
- Chỉ review diff mà không đọc code xung quanh — bug thường nằm ở chỗ code mới tương tác với code cũ, không chỉ trong dòng thay đổi.
- Bỏ qua review vì "code nhỏ, chắc không có gì" — bug nhỏ (off-by-one, thiếu await, thiếu null check) thường nằm ở diff nhỏ nhất.
- Sửa tất cả góp ý [Ý KIẾN] một cách máy móc — không phải mọi gợi ý đều đáng đánh đổi thời gian, ưu tiên bắt buộc và nên sửa trước.
- Merge ngay sau review mà không chạy lại test — review chỉ ra vấn đề bằng mắt, không thay thế việc xác nhận bằng test chạy thật.

## Phiên bản Claude Code
Đây là workflow Claude Code thuần, tận dụng khả năng đọc trực tiếp git diff và codebase.

Quy trình cụ thể:
1. Trong thư mục repo, đảm bảo branch cần review đã checkout hoặc biết tên branch để so sánh.
2. Chạy `claude`, yêu cầu: `"Chạy git diff main...ten-branch, review theo checklist bảo mật/logic/edge-case, phân loại mức độ."` — để Claude Code tự gọi `git diff` qua Bash thay vì bạn copy-paste tay.
3. Nếu có sẵn skill `code-review` trong hệ thống (`/code-review` hoặc skill tương đương), ưu tiên dùng — nó đã đóng gói checklist chuẩn.
4. Với PR lớn/nhiều file, cân nhắc dùng Agent tool để launch 1 subagent review độc lập (không chia sẻ context với phiên vừa code) — tránh thiên vị đã nêu ở Common mistakes.
5. Lệnh mẫu: `claude "Đóng vai reviewer độc lập chưa từng thấy code này. Review git diff main...feature/checkout-v2 theo 5 tiêu chí: logic, edge case, bảo mật, độ phức tạp, test coverage."`
6. Sau khi có danh sách phát hiện, xử lý xong [BẮT BUỘC SỬA], chạy lại test suite (`npm test`/`pytest`), rồi mới `git merge` hoặc tạo PR trên GitHub qua `gh pr create`.

## Khi nào nên dùng Deep Research
Hầu như không cần cho code review thông thường — review dựa trên logic và convention nội bộ, không cần nguồn ngoài. Ngoại lệ: khi review liên quan đến 1 lỗ hổng bảo mật cụ thể (vd cách xử lý JWT, OAuth flow) mà bạn không chắc best practice hiện tại — lúc đó tra cứu tài liệu bảo mật chính thức (OWASP, docs của thư viện auth đang dùng) trước khi kết luận, thay vì tin hoàn toàn vào nhận định của Claude.
