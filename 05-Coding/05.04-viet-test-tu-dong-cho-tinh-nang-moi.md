# Viết test tự động cho tính năng mới

## Mục tiêu
Có bộ test tự động (unit + integration cần thiết) cho 1 tính năng mới, cover đúng các case rủi ro cao (không phải 100% coverage vô nghĩa), viết xong và pass trong 20-40 phút.

## Khi nào dùng
- Vừa implement xong (hoặc đang implement) 1 tính năng/hàm có logic đủ phức tạp để đáng lo lắng về bug.
- Tính năng có nhiều edge case (validate input, tính toán, xử lý trạng thái) chứ không phải CRUD đơn giản.
- Không dùng workflow này để chạy đua coverage 100% cho code đơn giản (getter/setter, UI thuần hiển thị) — lãng phí thời gian, ưu tiên chỗ có logic rủi ro thật.

## Input
- Đoạn code/hàm cần test (hoặc để Claude Code tự đọc file trong repo).
- Mô tả hành vi mong đợi: input nào → output nào, kể cả case lỗi mong đợi ra sao.
- Framework test đang dùng trong project (Jest, Pytest, Vitest...) — để Claude Code không đề xuất framework khác.
- (Tuỳ chọn) Các bug đã từng xảy ra ở tính năng tương tự trước đây — để test cover luôn regression.

## Prompt Template
```
Bạn là kỹ sư viết test, ưu tiên test đúng chỗ rủi ro cao thay vì chạy theo số lượng test case.

Code cần test:
{{dán code hoặc đường dẫn file}}

Hành vi mong đợi:
{{mô tả input -> output, kể cả case lỗi/exception mong đợi}}

Framework test: {{Jest / Pytest / Vitest / ...}}

Yêu cầu:
1. Trước khi viết test, liệt kê danh sách case cần cover: happy path, edge case (rỗng/null/biên), case lỗi mong đợi.
2. Viết test theo TDD nếu code chưa có: viết test trước (test sẽ fail), sau đó implement/sửa code để pass.
3. Nếu code đã có sẵn: viết test, chạy thật để xác nhận pass, không suy đoán "chắc sẽ pass".
4. Test phải độc lập (không phụ thuộc thứ tự chạy), có tên rõ nghĩa (mô tả case đang test, không phải "test1", "test2").

Sau khi viết xong, chạy test suite thật và dán kết quả (pass/fail) vào output.
```

## Checklist
- [ ] Danh sách case được liệt kê trước khi viết test — kiểm tra có thiếu case rủi ro nào không.
- [ ] Test thực sự được chạy (không phải "viết xong là coi như pass") — có kết quả pass/fail thật kèm theo.
- [ ] Tên test case đủ rõ để đọc là hiểu đang test gì, không cần đọc code bên trong.
- [ ] Test không phụ thuộc lẫn nhau hoặc phụ thuộc thứ tự chạy.
- [ ] Có ít nhất 1 test cho case lỗi (input sai/exception), không chỉ toàn happy path.
- [ ] Xoá/gộp test trùng lặp không thêm giá trị (test cùng 1 logic nhiều lần với input gần giống nhau).

## Expected Output
Bộ test chạy pass thật (có log kết quả thật, không phải mô tả bằng lời), cover happy path + ít nhất 2-3 edge case quan trọng + 1 case lỗi. Tên test rõ ràng kiểu `should return 400 when email is invalid` chứ không phải `test case 3`. Nếu code có bug, test nên fail và chỉ đúng chỗ sai — đó là dấu hiệu test có giá trị thật, không phải test viết cho có.

## Common mistakes
- Chấp nhận báo cáo "đã viết test" mà không yêu cầu chạy thật — Claude Code có thể viết test cú pháp đúng nhưng logic assert sai, chỉ chạy thật mới lộ ra.
- Chạy theo số lượng test case thay vì độ phủ rủi ro — 20 test na ná nhau cho happy path nhưng thiếu test cho case input rỗng vô dụng hơn 5 test đúng chỗ.
- Không test case lỗi/exception — chỉ test khi mọi thứ đúng, bỏ qua khi hệ thống nhận input sai (đây là nơi bug production hay xảy ra nhất).
- Viết test phụ thuộc trạng thái/thứ tự chạy (test B cần test A chạy trước) — test suite trở nên giòn, fail ngẫu nhiên khi chạy song song hoặc đổi thứ tự.
- Để Claude Code tự sửa code cho khớp với test thay vì sửa test cho khớp hành vi đúng — nếu test fail, cần xác định lỗi ở code hay ở kỳ vọng test trước khi sửa bên nào.

## Phiên bản Claude Code
Đây là workflow Claude Code thuần — cần chạy test thật, không chỉ viết văn bản mô tả test.

Quy trình cụ thể:
1. Trong thư mục project, chạy `claude`. Nếu áp dụng TDD chuẩn (feature chưa code), yêu cầu rõ: "Viết test trước theo TDD, xác nhận test fail đúng lý do, sau đó mới implement code để pass" — nếu hệ thống có skill `superpowers:test-driven-development`, dùng nó cho đúng flow.
2. Cấu trúc thư mục thường gặp: test đặt cạnh file nguồn (`checkout.ts` + `checkout.test.ts`) hoặc trong `/tests` riêng theo convention project — nói rõ convention này trong prompt để Claude Code đặt file đúng chỗ.
3. Lệnh mẫu: `claude "Đọc src/lib/pricing.ts, liệt kê case cần test, viết test bằng Vitest, chạy npm test và dán kết quả."`
4. Bắt buộc để Claude Code tự chạy lệnh test qua Bash (`npm test`, `pytest -v`, `go test ./...`) và dán output thật vào phản hồi — không chấp nhận câu trả lời chỉ có code test mà không có kết quả chạy.
5. Dùng TodoWrite để theo dõi danh sách case cần cover khi tính năng phức tạp (nhiều nhánh logic) — tránh bỏ sót case giữa chừng khi phiên làm việc dài.
6. Sau khi test pass, chạy full test suite (không chỉ file test mới) để đảm bảo không phá vỡ test cũ — 1 lệnh duy nhất, không cần hỏi lại.

## Khi nào nên dùng Deep Research
Hầu như không cần cho việc viết test thông thường. Ngoại lệ: khi test liên quan đến hành vi cụ thể của 1 API/thư viện bên ngoài (vd mock đúng response format của 1 payment gateway, hoặc test tích hợp với 1 service có edge case đặc thù) — lúc đó tra cứu tài liệu chính thức của service đó trước khi viết mock, để tránh test dựa trên giả định sai về hành vi thật của API.
